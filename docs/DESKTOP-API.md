# عقد تكامل تطبيق الدسكتوب

الدسكتوب يستخدم Supabase Auth نفسه. أنشئ موظفًا في لوحة الإدارة، ثم حسابًا له من الإعدادات. صلاحية `employee` للدسكتوب؛ صلاحية `manager` تتيح لوحة الويب أيضًا.

بعد `signInWithPassword`، أرسل توكن الجلسة في كل طلب:

```http
Authorization: Bearer <Supabase access_token>
Content-Type: application/json
```

الأساس في التطوير `http://localhost:3000`، وفي الإنتاج عنوان Vercel. لا تضع service-role key أو توكن تلكرام في الدسكتوب.

## بيانات الموظف والمهام

اقرأ `employees` و`tasks` و`daily_reports` من Supabase باستخدام جلسة الموظف. RLS يحصر البيانات به وبالمهام التي طُلبت مراجعته لها. اشترك في `postgres_changes` على `tasks` لاستقبال الإسناد وتغير الحالة.

`GET /api/desktop/directory` يعيد `id,name,profession` للموظفين لاختيار مراجع، دون أرقام الهاتف أو Telegram IDs.

## حالة المهمة

```http
PATCH /api/tasks/<task_id>

{"status":"in_progress"}
```

القيم: `todo`, `in_progress`, `done`. لا تغيّر الحالة مباشرةً عبر Supabase إذا أردت إرسال الإشعار: استخدم هذا المسار، فهو يحفظ الحركة ثم يرسل إشعار تلكرام. الإسناد من الويب يظهر تلقائيًا في Supabase Realtime.

## تسجيل الدوام

```http
POST /api/desktop/attendance

{
  "id":"<UUID ثابت للجلسة>",
  "work_date":"2026-09-07",
  "started_at":"2026-09-07T06:00:00.000Z",
  "ended_at":null,
  "attendance_seconds":3600,
  "active_seconds":3000
}
```

- يُستنتج الموظف من جلسة الدخول؛ لا تقبل الواجهة اختيار هوية موظف آخر.
- أرسل **القيم التراكمية** بنفس UUID عند التحديث، وليس زيادات الثواني. تكرار الإرسال لا يضاعف الدوام.
- `attendance_seconds` يشمل الخمول؛ `active_seconds` يستثنيه ولا يتجاوز الدوام.
- عند الخروج أرسل `ended_at` والقيم النهائية قبل التقرير اليومي.
- `work_date` تاريخ بداية الجلسة في بغداد. اقسم الجلسة عند منتصف الليل المحلي. أقصى مجموع دوام لليوم 86400 ثانية.
- خزّن التحديثات محليًا عند انقطاع الإنترنت وأعد إرسالها بالترتيب عند عودة الاتصال. الحقول الثابتة للجلسة لا تتغير، والقيم لا تنقص.

## التقرير اليومي

```http
POST /api/desktop/reports

{"day":"2026-09-07","summary":"أنجزت التصميم وبدأت مراجعة الملاحظات."}
```

الخادم يحسب ساعات التقرير من سجلات الدوام المحفوظة. يوجد تقرير واحد لكل موظف في اليوم؛ الإرسال التالي يحدّثه. أرسل جميع جلسات اليوم قبل إرسال التقرير.

## طلب مراجعة

```http
POST /api/reviews

{"task_id":"<UUID>","reviewer_id":"<employee UUID>","note":"يرجى مراجعة النصوص قبل الاعتماد."}
```

الموظف يطلب مراجعة مهمته فقط. يُحفظ الطلب أولًا ثم تُحاول خدمة تلكرام إشعار المراجع.

## الحذف والإشعارات

الحذف النهائي من لوحة الويب يلغي صلاحية الموظف ويحذف بياناته المرتبطة. تعامل مع `401` أو `403` بإيقاف المزامنة وطلب تسجيل دخول جديد؛ لا تُعد إرسال البيانات إلى هوية بديلة.

فشل إرسال تلكرام لا يلغي حفظ المهمة. تحتوي استجابة حركة المهمة على `notification` مثل `sent`, `disabled`, `unconfigured`, `failed`. يُسجّل فشل التسليم في `notification_deliveries`. لا توجد عملية خلفية دائمة أو إعادة إرسال دورية؛ الإرسال يحدث أثناء معالجة الطلب.

قد لا يمكن إشعار من أسند المهمة بتغير حالتها إذا لم يكن له سجل موظف مرتبط يحتوي Telegram ID. الموظف المكلّف يستقبل الإشعار متى اكتملت إعداداته.
